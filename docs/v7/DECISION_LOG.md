## D-01. Какой из двух триггеров публикации удалить (B01, Этап 0)

- **Решение:** удалить нативный Vercel cron (`vercel.json` → `crons`), оставить
  GitHub Actions `vercel-cron.yml` (4×/сутки + `workflow_dispatch`).
- **Альтернатива:** удалить GH workflow и оставить Vercel cron 06:00.
- **Обоснование:**
  1. коллизия именно в 06:00 — оба триггера бьют в `/api/cron` в одну минуту;
  2. на тарифе Vercel Hobby нативные кроны ограничены по частоте (1 раз/сутки),
     4×/сутки нативным кроном не получить — а 4×/сутки закрыты в GH workflow;
  3. GH workflow даёт ручной запуск (`workflow_dispatch`) и логирование
     HTTP-статуса в run-логах;
  4. изменение `vercel.json` безопасно для уже развёрнутого проекта (крон
     исчезнет после ближайшего деплоя; до деплоя остаётся двойной триггер —
     см. риск в отчёте Этапа 0).
- **Открытый вопрос владельцу:** подтвердите, что частота 4×/сутки (00/06/12/18
  UTC) — целевая. Если нужен другой график, правится `.github/workflows/vercel-cron.yml`.

## D-02. Kill-switch: дефолт PUBLISH_ENABLED

- **Решение:** `PUBLISH_ENABLED` по умолчанию `false`. После деплоя Этапа 0
  публикации не идут ни в одном процессе, пока владелец явно не включит флаг
  на единственном выбранном процессе-паблишере.
- **Альтернатива:** дефолт `true` (сохранить текущее поведение).
- **Обоснование:** вердикт двух ревью — NO-GO, прод уже страдает от дублей;
  стоп-кран обязан быть безопасным по умолчанию. Цена — пауза публикаций до
  явного включения владельцем.
- **Открытый вопрос владельцу:** на каком процессе включить `PUBLISH_ENABLED=true`
  после деплоя: (а) Vercel `/api/cron` (серверлесс), (б) Render-бот, (в) ни на
  каком до Этапа 1. Рекомендация — (в), до единого состояния.

## D-12. Клейм доставки ДО отправки (B07, Этап 5)

- **Решение:** `claim_delivery()` занимает слот `(job_hash, target_channel)` в
  леджере `deliveries` до отправки; занятый слот → паблишер пропускает
  отправку. `pending` старше 10 минут пере-клеймится (защита от крэша
  на середине отправки).
- **Альтернатива:** оставить как есть — `UNIQUE(job_hash, target_channel)`
  дедуплицирует строки, но не сообщения.
- **Обоснование:** измерено (мутационная проба 2026-09-05) — без клейма два
  паблишера дают **одну строку леджера и два поста в канале**, при этом тест
  Этапа 4 остаётся зелёным. То есть гейт «ноль дублей» до Этапа 5 не ловил
  исходный симптом инцидента.
- **Границы (зафиксировать при переносе):** (1) срабатывает только при
  `db is not None` — serverless-путь не защищён; (2) SQL диалекта SQLite —
  для PostgreSQL нужен `INSERT … ON CONFLICT DO NOTHING RETURNING` или
  advisory lock; (3) сбой леджера → fail-open с предупреждением в логе
  (сознательно: поломка хранилища не должна останавливать публикации, но
  `claim_delivery unavailable` должен быть в алертах).

## D-14. Хранилище на PostgreSQL (нулевая стоимость, Neon)

- **Решение:** добавлен `db_backend.py` — тонкий слой бэкендов. SQLite
  остаётся по умолчанию (без `DATABASE_URL` поведение байт-в-байт старое);
  при наличии `DATABASE_URL` выбирается PostgreSQL (Neon free tier). Схема
  портирована 1:1, сами запросы (~65 штук) не переписывались.
- **Механизм:** `translate_placeholders` (`?` → `%s`),
  `translate_upsert` (`INSERT OR IGNORE/REPLACE` → `ON CONFLICT …`),
  `ts_ago` (`datetime('now', ?)` → `now() - interval 'N min'`),
  `columns/tables` (`PRAGMA` → `information_schema`). Тестовая изоляция
  PostgreSQL: отдельная схема на `db_path` (md5) через `search_path`.
- **Обоснование:** на Render free ФС эфемерна — SQLite-файл стирается при
  рестарте, это и есть корень инцидента с дублями. Внешний бесплатный
  Postgres (Neon) решает проблему без платного плана Render.
- **Ограничения:** (1) `psycopg2-binary` добавлен в `requirements.txt`
  (ленивый импорт в `db_backend`); (2) `sslmode=require` добавляется к URL,
  если отсутствует — для локального/CI Postgres передавать `?sslmode=disable`;
  (3) `run_hash_migration` пропускается на Postgres (зависит от `rowid`
  SQLite). (4) Локальная проверка на живом Postgres в этом окружении
  недоступна (Docker daemon не запущен) — путь PostgreSQL гейтится в CI
  (`postgres-gate`, сервис `postgres:16` + `TEST_DATABASE_URL`). (5) Перед
  переключением с заполненной SQLite-базы нужен экспорт/импорт леджеров в PG;
  подключение к чистой PG с `PUBLISH_ENABLED=true` запрещено до верификации.
  Любой сбой claim теперь блокирует отправку, а не включает fail-open.

## D-15. Персистентность бота в БД (DbPersistence вместо PicklePersistence)

- **Решение:** `DbPersistence(BasePersistence)` хранит снимок состояния PTB
  (`user_data`/`chat_data`/`bot_data`/`conversations`) в таблице `bot_state`
  как `base64(pickle)`. Загружается при старте и сохраняется при каждом
  изменении `update_*`/`drop_*`, а `flush()` делает финальный снимок. В
  `render_main` подключается при наличии `db`, иначе фоллбэк на
  `PicklePersistence`-файл.
- **Обоснование:** `PicklePersistence` писал `bot_persistence.pkl` на
  эфемерную ФС Render → визард/профиль терялись при рестарте. Теперь
  состояние в разделяемой БД (Neon) и переживает рестарты. Сохранена
  семантика `PicklePersistence`: `pickle` бережёт int-ключи `user_id`/
  `chat_id` и произвольные объекты (JSON бы их сломал).
- **Ограничения:** тот же уровень доверия, что у `PicklePersistence` (pickle
  своего состояния, не внешних данных); таблица `bot_state` добавлена в DDL
  обоих диалектов и в карту upsert (`key`). Вызовы `update_*` синхронно
  записывают snapshot в БД, поэтому аварийный процесс теряет максимум текущую
  операцию, а не весь интервал до `flush()`.

## D-16. Безопасная обработка доставки и cutover

- **Решение:** и новые, и retry-публикации обязаны получить леджер-клейм до
  отправки. `claim_failed_delivery()` атомарно переводит `failed` в `pending`,
  поэтому два retry-worker не отправляют один payload одновременно. Ошибка
  леджера теперь fail-closed: отправка пропускается, а не выполняется
  «unguarded».
- **Соединение:** чтение через `DatabaseConnection` завершает транзакцию
  после fetch и один раз переподключается при operational error; SQLite
  получает `busy_timeout` и WAL в сериализованной фазе инициализации.
- **Cutover:** `migrate_db.py --import-sqlite PATH` открывает SQLite read-only,
  создаёт/дополняет PG-схему, идемпотентно переносит леджеры через
  `ON CONFLICT DO NOTHING` и синхронизирует BIGSERIAL. Порядок запуска:
  короткая пауза → `PUBLISH_ENABLED=false` → импорт → сверка counts →
  включение публикаций только на Render.
